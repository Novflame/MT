UI/UX Inventory and Navigation Map

Scope
- This inventory is limited to user experience, UI consistency, responsive design, light/dark modes, and visual identity.
- It is based on source-code inspection and the current known runtime status.
- Browser verification was not performed because the application was not running at the time of inspection.

A. Findings supported by source code

A1. Entry and public flows
1) /
- Purpose: root redirect based on session role.
- Role: all authenticated users and unauthenticated visitors.
- Structure: server component checks session and redirects to /dashboard, /teacher, /department-heads, /parent, /student, or /login.
- Shared layout: none; this is an entry redirect only.
- Navigation entry points: no user-facing navigation; it is a redirect layer.
- Discoverability: not intended as a landing page; it is infrastructure for route selection.
- Responsive/theme evidence: none beyond redirect logic.
- Apparent inconsistency: role-specific routing is handled centrally instead of a single shell.

2) /login
- Purpose: sign-in.
- Role: all users before authentication.
- Structure: centered card form with email, password, error banner, submit button, and a create-school call-to-action.
- Shared layout: standalone auth page; not part of dashboard shell.
- Navigation entry points: direct URL; registration link from the login form; no visible forgot-password link in the current source.
- Discoverability: direct and obvious for returning users; password recovery is not visibly surfaced.
- Responsive/theme evidence: the form uses a centered card, dark-mode classes, blue accent, rounded inputs, and a dark background shell.
- Apparent inconsistency: consistent with registration pattern, but no recovery affordance appears in source.

3) /register
- Purpose: school signup and initial admin onboarding.
- Role: school owner/principal setup flow.
- Structure: single card with header, logo, school registration fields, submit action, validation, and redirect to /login on success.
- Shared layout: standalone page; not part of dashboard shell.
- Navigation entry points: direct URL and login form link to /register.
- Discoverability: visible from login page only; no clear step-wise onboarding flow beyond the form itself.
- Responsive/theme evidence: uses min-h-dvh, responsive grid (single column on mobile, two columns on larger screens), dark:bg-slate-950, and blue gradient header.
- Apparent inconsistency: strong card form pattern but no visible completion-state or onboarding guidance beyond immediate redirect.

A8. Visual identity and styling pattern inventory
33) Core design language
- Default shell: dark sidebar + light main content for admin role screens.
- Use of blue as primary action and selected state accent.
- Neutral slate/white backgrounds with dark gray borders.
- Rounded cards and inputs; consistent border and shallow shadow system.
- Forms use label + input + validation error panel patterns.
- Navigations leverage Lucide icons and active-state highlighting by pathname.

34) Theme patterns
- Light/dark mode is implemented via a root .dark class and Tailwind dark variant.
- TopNavbar loads theme from localStorage and toggles document.documentElement.classList.toggle("dark", ...).
- Dark mode is used primarily for shell surfaces and some cards; light backgrounds remain the default content surface.
- Role shells differ slightly in implementation: main admin shell and department shell share the same dark-nav pattern but are not the same component tree.

35) Responsive patterns
- The app uses Tailwind responsive utilities (sm:, md:, lg:).
- Main dashboard shell changes content spacing and margin based on sidebar state.
- Mobile navigation hides the sidebar behind an overlay and toggles via a menu button.
- Content frequently stacks vertically on small screens and expands to multi-column layouts on larger screens.
- Some pages rely on card grids and minimum width constraints instead of a single global table component.
- Several document and certificate screens use custom fixed-height or print-oriented CSS; these are visually distinct from the general app shell.

C. Questions that cannot yet be answered
- Whether the dashboard shell truly disappears in practice when navigating between pages.
- Whether the language and theme controls remain reachable from all role flows beyond the source pattern.
- Whether the intended navigation model is a single persistent shell or multiple role-specific shells.
- Whether some pages are intentionally deep-link-only or simply under-discoverable.
- Whether registration and login flows are actually perceived as weak or confusing by real users.
- Whether password recovery exists outside the visible interface, even if no UI entry point is present in source.
- Whether the academic-year UI is perceived as context-setting or merely a disconnected management screen.
